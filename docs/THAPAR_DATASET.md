## Implemented scenarios and policies

The schema separates `issues`, `reports`, history, escalation, verification,
moderation, following, private messages, notifications and submission-idempotency
records. The new builder uses their existing services and the current category,
department, ward, staff-scope and dashboard policies. It does not fill a status
column to match the requested table.

`ReportSubmissionService` invokes the real clustering engine, including advisory
locking, GPS weights, adaptive category radius, confidence and extent caps.
Original decisions across 90 reports were 47 NEW_ISSUE, 39 MERGED, 2
MERGED_LOW_CONF, 1 SPLIT_LOW_CONF and 1 SPLIT_EXTENT_CAPPED. Moderation subsequently
moved two reports and marks their current decisions MANUAL; their original
decisions are preserved in the immutable moved-report audit. Current report
decisions are 47 NEW_ISSUE, 38 MERGED, 2 MERGED_LOW_CONF, 1 SPLIT_EXTENT_CAPPED,
and 2 MANUAL.

One supported split, one supported merge and one confidence confirmation have
actual moderation records. The open-manhole pair was conservatively separated
for low confidence, then reviewed and merged within its extent limit. The
pothole example actually refuses a merge at the extent cap. Unconfirmed
low-confidence/extent examples remain in grouping review.

`IssueLifecycleService`, verification/quorum services and escalation services
produce acknowledgements, scope-valid assignments, progress, repair claims,
rejected fixes/reopening, confirmations, timeout settlement, automatic closure,
reasoned administrative closure and rejection. Actions run in chronological
order with a thread-local injected historical clock in an isolated database.
Status history now uses the same transition timestamp as the issue, fixing an
uncontrolled wall-clock inconsistency. Ordinary requests retain their normal
clock, UUID and ticket sequence. Evaluation seed identities remain compatible;
dataset tickets use the separate `D` reference prefix.

There are 71 registered and 19 anonymous reports. Only eligible reporting
citizens vote, with existing uniqueness/quorum rules. The seed includes 14 votes,
16 private clarification messages, 9 followers, 83 in-app notifications and 104
recorded escalation events at import. Eleven records have actual resolution
timestamps: four on time and seven late. Pending-verification clocks are paused.
Live scheduled escalation had increased the sample event count to 109 at the
final 2026-11-10T21:43Z check. The application remains live: ages, priorities,
escalations and eventually statuses advance naturally after import.

Dashboard reads exercise reported/resolved trends, multiple backlog age bands,
ward summaries, department/staff metrics and mixed SLA outcomes. Existing
minimum-sample suppression remains: a small department cohort still displays
insufficient data rather than an invented percentile. Email delivery and
email-based password recovery remain deferred; no email service was enabled.

## Replacement and repeatability

Implementation entry points:

- `scripts/thapar_dataset_plan.py`: seeded spatial/scenario plan using current
  database polygons and category policy.
- `scripts/prepare_thapar_assets.py` and
  `scripts/data/thapar-demo-v2-assets.json`: explicitly synthetic evidence,
  content-addressed upload identities and reusable public URL catalogue.
- `ThaparDatasetGenerator` / `application-thapar-dataset.yml`: real-service
  execution, evidence validation and controlled clock; profile/authorization,
  loopback JDBC and owned database-name guards refuse production generation.
- `scripts/refresh_thapar_dataset.py`: owned PostGIS clones, verification,
  checksummed sample-only export and guarded atomic import.
- `scripts/refresh-thapar-demo.sql`: guarded retirement phase only; refuses
  standalone execution without the Python transaction's validated ID tables.

Retirement requires exact legacy UUID/reference/device/description identities,
or the validated v2 namespace. A real report attached to a demo cluster, a
cross-scope merge link or moderation dependency causes refusal for review.
Deterministic identities, existing-citizen reuse and collision checks prevent
duplicates. New accounts use real BCrypt hashes of a securely generated password;
existing account rows are never overwritten. Report/issue/dependent rows are
staged, checked and installed in one repeatable-read transaction with bounded
locks and unrelated-row fingerprints. The normal ticket sequence is not reset.
The target's public API ward identities and preserved QA reference must match
the private database connection before apply. A fresh backup precedes apply.

Rehearsal restored the source into a separately owned database. It verified
mixed-evidence refusal, forced-failure rollback with identical table fingerprints,
successful first replacement, and a second replacement with 50/90 and zero new
duplicate users. Two independent isolated builds produced equal business-row
fingerprints across all eleven exported tables. BCrypt salts and auto-assigned
audit IDs are intentionally excluded from that semantic comparison.

To reproduce, use a **new** artifact state path and a private Python tool
environment (tested psycopg 3.2.13), Java/Maven and Docker. No application package
upgrade is required. Image regeneration additionally uses Pillow (tested 11.3.0).
The approved catalogue is reused without reuploading on repeat runs. An arbitrary
new seed/scenario set requires reviewing its matching catalogue; mismatches fail.
Supply database credentials privately in `backend/.env.seed` and the actual cloud
and upload preset via `frontend/.env.local`; never commit these files.

```bash
# Set dataset_python to the Python executable in your private tool environment.
dataset_state=artifacts/thapar-refresh-review/state.json
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" prepare \
  --seed 731109 --anchor 2026-11-10T20:36:11Z
# For exact old-source reproduction, also supply --backup <the original dump.gz>.
# On a future date, choose a reviewed current anchor for recent interactive work.
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" test
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" build
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" repeat
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" compare
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" export
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" rehearse
# Only for an explicitly authorized deployed refresh after reviewing the evidence:
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" apply --apply-deployed
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" verify
"$dataset_python" scripts/refresh_thapar_dataset.py --state "$dataset_state" cleanup
```

Cleanup validates its recorded Docker container ID and removes only that task's
container. It retains backups and evidence; it does not stop the user's local
frontend, backend, database or another agent's containers.
